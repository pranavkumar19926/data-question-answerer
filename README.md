# Data Question Answerer — Beginner-Friendly Project Guide

> **Start here if you have never studied this code before.** This guide explains the purpose of the project, what happens when you ask a question, why each file exists, how the important functions work, how to run the project, and what you should understand before explaining it in an interview.

---

## 1. What is this project?

**Data Question Answerer** lets a person ask questions about data using ordinary English instead of writing SQL manually.

For example, imagine a database containing crop production records. Normally, to find the three states with the highest wheat production in 2022, you would need to know SQL and write a query such as:

```sql
SELECT s.state_name, SUM(p.production_tonnes) AS total
FROM production p
JOIN states s ON p.state_id = s.state_id
JOIN crops c ON p.crop_id = c.crop_id
WHERE c.crop_name = 'Wheat' AND p.year = 2022
GROUP BY s.state_name
ORDER BY total DESC
LIMIT 3;
```

A user of this project does not need to write that query. They can simply type:

> Top 3 states by wheat production in 2022?

The application sends the question and the database schema to a language model. The model produces SQL. The application checks that SQL, executes it against SQLite in read-only mode, and displays the result.

Depending on which interface you use, the result can include:
- A plain-English summary.
- The SQL query generated by the model.
- The returned table rows.
- A bar chart when the result has a suitable category and numeric column.
- A message that the question cannot be answered from the available data.

The project has **two main ways to ask questions**:

1. **Curated-data application** — asks questions about the agriculture databases already prepared by the project. This includes a small teaching dataset and a larger district-level dataset.
2. **CSV upload application** — lets a user upload a CSV file and ask questions about the columns in that file.

There is also a document-search feature that can answer some questions from local Markdown notes. This is a small retrieval-based feature; it does not use a vector database or embedding model.

## 2. Important beginner concepts

Before reading the source code, understand these terms.

| Term | Meaning in this project |
|---|---|
| CSV | A text file that stores data in rows and columns, often opened with Excel. |
| Database | An organised place to store and retrieve data. |
| SQLite | A lightweight database engine. The project stores its tables in local `.db` files. |
| Table | Data arranged in rows and columns, like a spreadsheet sheet. |
| Row / record | One individual entry in a table. |
| Column | One property of a record, such as state name or production. |
| SQL | The language used to ask a database for data. |
| SELECT | SQL command that reads data. |
| JOIN | Combines related tables using a common column. |
| WHERE | Filters rows based on a condition. |
| GROUP BY | Groups rows so calculations can be done per group. |
| SUM / AVG / COUNT | SQL functions for total, average, and number of records. |
| LIMIT | Restricts how many result rows are returned. |
| LLM | Large Language Model: software trained to understand and generate language. |
| Prompt | Instructions and context sent to the LLM. |
| Text-to-SQL | Converting a natural-language question into an SQL query. |
| Schema | The structure of a database: its tables, columns, and data types. |
| Catalog | Human-readable descriptions of the tables and columns. |
| Read-only | The database connection is opened so queries can read data, not change it. |
| Retry | Trying again after a generated query fails. |
| Evaluation | Running a fixed set of questions to measure how often expected answers are found. |
| RAG | Retrieval-Augmented Generation: finding relevant source material and using it to answer a question. |
| Streamlit | A Python library used here to build browser-based interfaces. |
| Ollama | A tool that runs supported LLMs locally on your computer. |

**states**

| state_id | state_name |
|---:|---|
| 1 | Punjab |

**crops**

| crop_id | crop_name |
|---:|---|
| 1 | Rice |

## 3. Architecture at a glance

### 3.1 Curated database workflow

```text
User question
     |
     v
CLI (app/chain.py) or Streamlit UI (app/ui.py)
     |
     v
Choose a prompt version and attach the database catalog
     |
     v
LLM provider (app/llm.py)
     |-- OpenAI, if configured and working
     |-- Ollama, if running and a model is available
     |-- Rule-based fallback, if neither provider works
     |
     v
Generated SQL or UNANSWERABLE
     |
     v
Safety validation (app/safety.py)
     |
     v
SQLite connection opened in read-only mode
     |
     v
Execute SQL and fetch rows
     |
     v
Build a simple answer summary + log request
     |
     v
Return SQL, answer, rows, attempts
     |
     v
CLI output or Streamlit table/chart
```

### 3.2 CSV upload workflow

```text
User uploads CSV in app/upload_app.py
     |
     v
app/anydata.py reads the CSV with pandas
     |
     v
Clean column names and create a SQLite table
     |
     v
Inspect columns and sample values to create a catalog
     |
     v
User types a question
     |
     v
Build a generic prompt containing the table and its columns
     |
     v
Ollama generates SQL in JSON format
     |
     v
Safety validation and read-only SQLite execution
     |
     v
Return an answer + SQL + rows
     |
     v
Streamlit displays the rows and, where possible, a bar chart
```

### 3.3 Document retrieval / hybrid workflow

```text
Question
   |
   v
app/hybrid.py classifies it using keyword rules
   |-- DB question ------> app/chain.py
   |-- Documentation ---> search local Markdown passages
   |-- Both ------------> database answer + document context
   |
   v
Return answer and document filename citations (when applicable)
```

**Important:** The code in `app/hybrid.py` uses keyword overlap to retrieve passages. It is a simple retrieval implementation, not semantic vector search. There are no embeddings or vector database in this implementation.

## 5. The database: what data does the project contain?

There are two agriculture datasets in the main database.

### 5.1 Small teaching dataset

Run:

```bash
python app/load_db.py
```

This creates `db/app.db` and three tables:

- `states`: six example Indian states, their regions, and geographic areas.
- `crops`: five crops and their growing seasons.
- `production`: production and area values associated with state, crop, and year.

The production records in this small dataset cover 2021 and 2022. The values are a compact project/demo dataset, not a complete official national production database.

### 5.2 Real district-level dataset

The repository contains `data/raw/Crops_data.csv`. Run:

```bash
python app/load_real.py
```

This reshapes the original wide-format CSV into a long-format table named `real_crop_production` inside the same `db/app.db`.

The project documentation records 34,902 resulting records, 20 states, 23 crops, and years 2010–2017. The measurement units are important:

- `area_1000ha`: area in thousands of hectares.
- `production_1000tons`: production in thousands of tonnes.
- `yield_kgpha`: yield in kilograms per hectare.

Do not describe `production_1000tons` as ordinary tonnes. For example, a stored value of 125 means 125 thousand tonnes.

The source notes in `EVIDENCE.md` explain that the CSV was obtained from a GitHub-hosted dataset mirror in a data.gov.in-style format. The README's description of it should not be confused with a direct live API connection to data.gov.in.

### 5.3 The catalog

Open `app/catalog.json`. This file describes tables and columns in plain English.

For example, it tells the SQL model that:
- `states.state_name` contains a readable state name.
- `crops.season` contains Kharif, Rabi, or Annual.
- `production.production_tonnes` stores production measured in tonnes.
- The production table connects to the state and crop tables using their IDs.

Why is this necessary? A model cannot reliably write SQL if it does not know the available tables, column names, data types, and relationships. The catalog gives it that context.

## 6. Main execution flow — follow one question from beginning to end

Let's use this example:

> Top 3 states by wheat production in 2022?

### Step 1: The question enters `chain.py`

The command-line interface reads text from the terminal. The Streamlit interface can also call the same `answer()` function.

The important function is:

```python
answer(question: str, retries: int = 3, prompt_version: str = "v2")
```

- `question` is the user's text.
- `retries` controls how many attempts are allowed if query generation or execution fails.
- `prompt_version` chooses one of the prompt files.

### Step 2: The application asks `llm.py` for SQL

The function `llm_sql()` imports `get_sql()` from `llm.py`.

The model receives:
1. The instructions from a prompt file.
2. The database catalog.
3. The user's question.

It is instructed to return JSON in this shape:

```json
{"sql": "SELECT ..."}
```

For a question outside the data, it should return:

```json
{"sql": "UNANSWERABLE"}
```

### Step 3: The provider is selected

In `llm.py`, `get_sql()` tries providers in this order:

1. **OpenAI** — only when `OPENAI_API_KEY` is set and the required integration can be imported and used. The code uses `gpt-4o-mini` through `langchain-openai`.
2. **Ollama** — the code checks the local Ollama server at `http://localhost:11434`, discovers the installed models, and sends a generation request. `LLM_MODEL` can request a particular installed model.
3. **Rule-based fallback** — if the external model routes fail, `rule_sql()` uses Python keyword and pattern checks to support a limited set of known question types.

The fallback is not an LLM. It is a collection of explicit Python conditions that return prewritten SQL for supported patterns. This helps demonstrate and test the workflow without a model API.

### Step 4: The generated SQL passes through the safety gate

The function `run_sql()` in `chain.py` first calls:

```python
validate_sql(sql, max_rows)
```

This happens before executing the query.

The validator checks that the SQL begins with `SELECT`, rejects semicolon-separated statements, rejects a list of SQL write/administrative keywords, and adds a row limit if the query does not contain one.

### Step 5: SQLite runs the query in read-only mode

The connection uses a URI like:

```python
sqlite3.connect(f"file:{DB}?mode=ro", uri=True)
```

The `mode=ro` option asks SQLite to open the existing database read-only. The program then executes the validated SQL and fetches the rows.

The result rows are converted into dictionaries so they are easier to pass to the UI and convert into a pandas DataFrame.

### Step 6: The application produces a summary

The `answer()` function checks whether rows were returned.

- If no rows match, it returns a message saying so.
- If rows exist, it reports the number of rows and displays information from the first row.
- If the first row contains an alias called `total`, it adds a simple total/top-value sentence.

This is a lightweight formatter. It is not a second LLM call and it does not generate a sophisticated natural-language explanation for every possible table shape.

### Step 7: The request is logged

The application calls `log_event()` from `trace.py`. It stores information such as the question, SQL, status, attempts, elapsed time, and estimated cost in `logs/queries.jsonl`.

The output is returned to the CLI or Streamlit UI.

## 7. File-by-file source code guide

This section explains what each source file is responsible for and how its main blocks work. It focuses on the actual code structure and important statements, rather than pasting every source file again.

### 7.1 `app/chain.py` — the main question-to-database pipeline

This is the central orchestration file for the curated-data CLI.

**Imports**

- `json`: formats the final result as JSON for terminal output.
- `sqlite3`: connects to the SQLite database.
- `sys`: reads command-line arguments.
- `time`: measures how long a request takes.
- `Path`: constructs file paths safely.
- `log_event` and `estimate_cost`: come from `trace.py`.
- `validate_sql`: comes from `safety.py`.

The `try/except ImportError` around the trace import supports running the file as a script or importing it as part of the `app` package.

**Project paths**

- `ROOT` points to the repository root.
- `DB` points to `db/app.db`.
- `CATALOG` loads the JSON database catalog into Python.

**`run_sql(sql, max_rows=100)`**

1. Calls `validate_sql` before touching the database.
2. Opens SQLite using `mode=ro`.
3. Sets `row_factory = sqlite3.Row`, allowing each row to be accessed by column name.
4. Executes the safe query and fetches all returned rows.
5. Converts each row to a normal dictionary.
6. Closes the connection in a `finally` block, including when execution raises an error.

**`llm_sql(question, prompt_version="v2")`**

1. Imports the `get_sql` function from `llm.py`.
2. Calls it with the question and selected prompt version.
3. Receives two values: generated SQL and a provider label.
4. Prints which provider was used, or warns that the rule fallback is active.
5. Returns the SQL string to the main pipeline.

**`answer(question, retries=3, prompt_version="v2")`**

1. Records the start time.
2. Initialises `last_err` to an empty string.
3. Starts a loop from attempt 1 up to the retry limit.
4. Calls the SQL generator. After a failed attempt, the previous database error is appended to the next question as a correction hint.
5. If SQL generation returns `UNANSWERABLE`, it immediately returns a safe “cannot answer” response and logs that status.
6. Otherwise, it calls `run_sql()`.
7. If the query succeeds, it builds a basic explanation and returns answer text, validated SQL, rows, and attempt count.
8. If execution raises an exception, it records and prints the error, then proceeds to the next attempt.
9. If all attempts fail, it returns a failure message and logs the failure.

**`stream_print(text, delay=0.015)`**

Prints one character at a time and waits briefly between characters. This creates a streaming-like terminal effect. It is a display effect; the function is not receiving true token streaming from the LLM.

**The `__main__` block**

This block runs only when you execute `chain.py` directly.

- Reads terminal arguments.
- Removes the `--stream` flag.
- Detects a prompt-version flag from `--v1` through `--v6`.
- Detects `--real`, which selects prompt v6.
- Joins the remaining arguments into the user's question.
- Calls `answer()`.
- Prints either normal JSON or the SQL, character-by-character answer, and rows.

### 7.2 `app/llm.py` — model connection and SQL generation

This file separates language-model logic from database execution.

**Imports and catalog path**

- `json` parses the model's structured response.
- `os` reads environment variables.
- `Path` finds the prompt and catalog files.
- `CATALOG_PATH` points to `app/catalog.json`.

**`_catalog_text()`**

Reads the catalog as UTF-8 text and limits the returned text to the first 4,000 characters. This catalog text is inserted into the prompt.

**`_prompt(version="v2")`**

1. Accepts only versions v1 through v6; otherwise it selects v2.
2. Builds the filename such as `v4_sql.txt`.
3. Reads the selected prompt.
4. Replaces the `{catalog}` placeholder with the catalog text.
5. Returns the complete prompt string.

**`rule_sql(question)`**

This is the no-model fallback. It lowercases the question, detects known state and crop names, and checks for known phrases such as “top”, “total rice”, “average wheat”, and “which Kharif crops”.

Each matching condition returns a fixed SQL string. If none of the supported patterns match, it returns `UNANSWERABLE`.

This fallback is deliberately limited. It is not a general natural-language understanding system, and it does not provide the same flexibility as an LLM.

**`get_sql(question, prompt_version="v2")`**

This is the provider-selection function.

- It first prepares the selected prompt.
- If `OPENAI_API_KEY` exists, it tries to initialise `ChatOpenAI` with model `gpt-4o-mini` and temperature zero, then requests structured dictionary output.
- If OpenAI fails or is not configured, it tries Ollama using HTTP requests.
- It asks Ollama for JSON output and extracts the `sql` value from the response.
- It checks that the returned value is a string and starts with `SELECT`, unless it is `UNANSWERABLE`.
- If Ollama is unavailable or fails, it calls `rule_sql()`.

**Why temperature zero?** The project uses SQL generation as a repeatable, constrained task. A low temperature reduces variation, although it does not guarantee correctness.

### 7.3 `app/safety.py` — SQL safety checks

This file defines a list called `FORBIDDEN`. It contains SQL commands such as `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, and other operations that can modify database state or perform administrative actions.

**`validate_sql(sql, max_rows=100)` works as follows:**

1. Removes whitespace around the SQL and strips a trailing semicolon.
2. Converts a copy to lowercase to make keyword checks case-insensitive.
3. Requires the statement to begin with `SELECT`.
4. Splits the text into tokens and checks for forbidden commands.
5. Rejects an internal semicolon, which can indicate statement stacking.
6. Adds `LIMIT 100` (or the supplied maximum) if the query has no `LIMIT`.
7. Returns the validated SQL string.

**A critical engineering note:** this is a lightweight string-based validator, not a full SQL parser or a formal security boundary. Keyword matching can have edge cases, and a query that already contains a larger LIMIT is not reduced to 100 by this function. The read-only SQLite connection is an additional safeguard. For production use, replace or strengthen this validation with SQL parsing, strict table/column allow-lists, an enforced result cap, and a database account/connection that has only the permissions the application needs. Do not claim that the current string checks alone make arbitrary generated SQL completely safe.

### 7.4 `app/anydata.py` — engine for uploaded CSV files

This file contains the logic used by the upload interface. It does not contain Streamlit widgets.

**Imports**

- `io` reads uploaded bytes as a file-like object.
- `json` handles JSON responses from Ollama.
- `os` reads environment settings.
- `re` cleans names and extracts JSON when needed.
- `sqlite3` stores and queries uploaded data.
- `time` measures elapsed time.
- `Path` builds paths.
- `pandas` loads and transforms CSV data.
- `validate_sql` reuses the SQL safety function.

**Database setup**

- `ROOT` identifies the project folder.
- `UPLOAD_DB` points to `db/uploads.db`.
- `mkdir(parents=True, exist_ok=True)` creates the database directory if it does not exist.

**`clean(name)`**

Converts a column or table name to lowercase, replaces runs of non-word characters with underscores, and removes underscores at the ends. It returns `col` if the cleaned string becomes empty.

Example: `"Student Name"` becomes `"student_name"`.

**`load_upload(file_bytes, filename, max_rows=50000)`**

1. Reads the uploaded CSV bytes with pandas.
2. First tries UTF-8 with a byte-order-mark-friendly encoding; if that fails, tries Latin-1.
3. Cleans the column names.
4. Makes duplicate column names unique by appending suffixes such as `_2`.
5. Keeps only the first 50,000 rows if the uploaded file is larger.
6. Creates a table name using the uploaded filename.
7. Writes the DataFrame to `uploads.db`, replacing a table with the same name.
8. Calls `describe_table()` to create a simple catalog.
9. Returns the table name, row count, columns, catalog, and first five rows.

**`describe_table(table)`**

1. Opens the uploads database in read-only mode.
2. Reads up to 200 rows from the selected table into pandas.
3. Checks each DataFrame column's inferred type.
4. Assigns `INTEGER`, `REAL`, or `TEXT`.
5. Stores up to three distinct sample values as a basic clue about what the column means.
6. Returns a dictionary describing the table and its columns.

**`generic_prompt(catalog)`**

Builds SQL-writing instructions for an arbitrary uploaded table. It includes the table name, description, column names, data types, and sample values.

The prompt tells the model:
- Use only the one uploaded table.
- Generate one SELECT statement.
- Keep the query within the row limit.
- Use SUM, AVG, COUNT and GROUP BY for the appropriate question types.
- Return `UNANSWERABLE` when the requested information is not present.

**`_ollama(prompt_text)`**

1. Calls Ollama's local tags endpoint to find installed models.
2. Uses `LLM_MODEL` when it matches an installed model; otherwise selects the first available model.
3. Sends the prompt to Ollama's generate endpoint.
4. Requests JSON output and temperature zero.
5. Extracts the SQL string from the JSON response.
6. Returns the SQL and a source label such as `ollama:qwen2.5-coder:7b`.

Unlike `llm.py`, this upload-specific function calls Ollama directly. It does not try the OpenAI provider or the rule fallback.

**`run_upload_sql(sql, max_rows=100)`**

Validates SQL, opens `uploads.db` read-only, executes the query, converts rows to dictionaries, and closes the connection.

**`ask_any(question, table, catalog, retries=2)`**

1. Builds a prompt from the uploaded file's catalog.
2. Repeatedly asks Ollama for SQL, up to the configured number of attempts.
3. Returns a model-not-reachable message if Ollama cannot be contacted.
4. Returns an unanswerable response if the model declines the question.
5. Otherwise, validates and executes the query.
6. Produces a small summary and returns answer, SQL, rows, source, attempt count, and elapsed time.
7. If SQL execution fails, adds the error to the next prompt as a correction hint.
8. Returns a failure message after the retry limit.

**`pick_chart(df)`**

Returns no chart choice when the result is empty, has fewer than two columns, has no numeric column, has no categorical column, or has more than 100 rows. Otherwise, it picks the first categorical column as x and the first numeric column as y.

### 7.5 `app/upload_app.py` — CSV upload user interface

This is the Streamlit interface for arbitrary CSV files.

- Adds the folder containing the app to Python's import path so local modules can be imported.
- Imports pandas, Streamlit, and the three functions it needs from `anydata.py`.
- Configures the browser page title and wide layout.
- Creates Streamlit session-state keys for the uploaded table, catalog, upload metadata, result, and question. Session state keeps values between Streamlit reruns.
- Displays a file uploader restricted to CSV files.
- When a new file is uploaded, reads its bytes and builds a cache key from its filename and size.
- If that key has changed, calls `load_upload()` and stores the returned table information in session state.
- Displays a preview of the first five rows.
- Calls `st.stop()` if no table has been uploaded, preventing the question form from being shown before data exists.
- Displays a question form and calls `ask_any()` when the user submits a non-empty question.
- Displays the answer and SQL.
- Converts result rows into a pandas DataFrame and displays the table.
- Calls `pick_chart()` and renders a bar chart when the returned x/y columns are usable.
- Shows the source provider and number of attempts.

### 7.6 `app/ui.py` — curated agriculture Streamlit interface

This is the browser UI for the prepared agriculture datasets.

- Imports Streamlit and pandas.
- Imports `answer()` from `chain.py` and `hybrid_answer()` from `hybrid.py`.
- Creates the page title and a radio control to choose automatic DB-vs-documents routing or database-only mode.
- Defines sample questions to help users get started.
- Reads the question text from a text input.
- When the question is processed, calls `hybrid_answer()` in Auto mode or `answer()` in Database-only mode.
- Shows the chosen route and number of attempts.
- Displays generated SQL when available, the answer, citations when present, and the result rows.
- Attempts to plot the first column against the second when the second column is numeric.

### 7.7 `app/hybrid.py` — local document retrieval and routing

This module combines database question answering with a small local-document search.

**`passages()`**

- Finds Markdown files in `data/docs/`.
- Reads each file as UTF-8.
- Splits the text on Markdown headings.
- Keeps non-trivial passages and records the source filename.
- Limits each stored passage to 800 characters.

**`docs_rag(question, k=2)`**

- Extracts lowercase alphabetic words from the question.
- Extracts words from each document passage.
- Scores each passage by the number of unique words shared with the question.
- Sorts passages from highest score to lowest.
- Returns up to `k` passages with a score greater than zero.

This is lexical retrieval: shared words produce a score. It does not understand synonyms or meaning in the way embedding-based retrieval can.

**`route(question)`**

Counts keyword matches against two lists:

- `DB_HINTS`: words associated with database questions, such as production, rice, state names, and years.
- `DOC_HINTS`: words associated with explanatory questions, such as “when”, “season”, “monsoon”, and “what is”.

It returns `db`, `docs`, or `hybrid` according to the counts. If neither list matches, it defaults to `docs`.

**`hybrid_answer(question)`**

- For `db`, sends the question to the database chain.
- For `docs`, retrieves local passages and returns their text with filenames as citations.
- For `hybrid`, obtains a database answer and appends relevant document context.
- If no passage is found for a document route, returns an unanswerable message.

### 7.8 `app/load_db.py` — creates the demo SQLite tables

This script creates the small agriculture database.

- Imports SQLite and `Path`.
- Defines the path to `db/app.db` and creates the parent directory.
- Defines Python lists containing state rows, crop rows, and production rows.
- Connects to SQLite and creates a cursor.
- Drops the old demo tables if they exist, so rerunning the script recreates them from the sample data.
- Creates the `states`, `crops`, and `production` tables.
- Declares the relationships from production to states and crops using foreign-key columns.
- Uses `executemany()` to insert the data lists efficiently.
- Commits the changes, prints the number of production records, and closes the connection.

**Important:** running this script recreates the three demo tables. It does not create the real-data table; that is the job of `load_real.py`.

### 7.9 `app/load_real.py` — transforms the real crop CSV

The input CSV is wide: a row contains district/year identifiers and many columns for crop-area, crop-production, and crop-yield measurements.

The database query workflow is easier when each row represents one district, one crop, and one year. This is called long or tidy format.

The script:

1. Reads `Crops_data.csv` using pandas.
2. Defines the identifier columns that describe the district and year.
3. Treats the remaining columns as measurement columns.
4. Uses a regular expression to identify the crop name and measurement type in each column name.
5. Groups the matching area, production, and yield columns for each crop.
6. Builds a separate DataFrame for each crop, retaining state, district, and year.
7. Concatenates those crop DataFrames into one long DataFrame.
8. Renames the columns to consistent database-friendly names.
9. Drops rows without production and rows where production is not positive.
10. Writes the result to `real_crop_production`.
11. Creates an index on state, crop, and year to help common filters.
12. Prints the row count, year range, number of states, and number of crops.

### 7.10 `app/datagovin.py` — generic CSV-to-database helper

This script is a general-purpose importer for CSV files with data.gov.in-style tabular data.

- `clean()` standardises column names.
- `load_csv()` reads a CSV, cleans its columns, limits the import to 50,000 rows, and stores it as a SQLite table.
- `update_catalog()` updates `app/catalog.json` with a new table entry and placeholder descriptions.
- The main block accepts a file path and optional `--table` name, or `--all` to process CSV files in `data/raw/`.

After using it, you should edit the generated catalog descriptions. The placeholder “EDIT ME” text is not meaningful schema documentation for an LLM.

### 7.11 `app/catalog.json` — database schema explained in plain language

This JSON file is not executable SQL. It is descriptive metadata for the language model and the developers.

Each table entry includes:
- Table name.
- Description of what one row represents.
- Column names.
- Column data types.
- Human-readable column meanings.

Keeping the catalog accurate is important. If the CSV schema changes but the catalog does not, the model may generate queries using wrong column names or misunderstand units.

### 7.12 Prompt files — `app/prompts/v1_sql.txt` to `v6_sql.txt`

These are instructions for the SQL-generating model. The versions are kept as separate files so the developer can compare prompt improvements.

| Version | Main purpose |
|---|---|
| v1 | Basic schema awareness, SELECT-only instruction, examples, and unanswerable behaviour. |
| v2 | Makes the three-table schema and supported values more explicit; adds counting and top-N instructions. |
| v3 | Adds rules for aliases, avoiding self-joins, year comparisons, single-value questions, totals, averages, and which table owns each column. |
| v4 | Adds threshold-question guidance, such as “above 30 million”, and an example. |
| v5 | Changes context to the real district-level table, its units, crops, states, and 2010–2017 year range. |
| v6 | Adds the key distinction between district-level values and state-level totals: a state question must aggregate across its districts. |

The prompt files use `{catalog}` as a placeholder. `llm.py` replaces that placeholder with the actual catalog text before sending the prompt.

A prompt is not a guarantee. The generated SQL still needs validation and testing.

### 7.13 `app/trace.py` — logging and rough cost estimate

**`log_event(ev)`**

- Creates the logs directory if needed.
- Adds a timestamp to the event dictionary.
- Appends one JSON object per line to `logs/queries.jsonl`.

JSON Lines (JSONL) is a format where every line is an independent JSON record. It is convenient for appending logs without rewriting the entire file.

**`estimate_cost(prompt_chars, completion_chars)`**

Calculates a rough estimated USD amount from character counts using the price assumptions written in the function. It is a rough approximation, not provider billing data or an exact token count. The same estimate should not be treated as accurate for Ollama, which runs locally.

### 7.14 `app/costs.py` — reads the request log

- Looks for `logs/queries.jsonl`.
- If it does not exist, prints a helpful message and exits.
- Parses each non-empty line as JSON.
- Counts successful, unanswerable, and failed requests.
- Calculates mean and maximum recorded latency.
- Adds the recorded estimated costs.
- Prints a summary.

### 7.15 `app/scale.py` — repeated evaluation timing

This script runs `app/eval_accurate.py` in a subprocess multiple times.

- Defaults to three runs.
- Reads a custom count after `--runs`.
- Measures each run's wall-clock time.
- Checks whether the output contains the expected `28/28` success text.
- Stops if a subprocess exits with an error.
- Reports the mean, minimum, and maximum run time and a rough per-question time.

The script is a small repeatability/timing exercise. It is not a production load test with many concurrent users.

### 7.16 `app/eval.py` — older evaluation runner

This file is explicitly marked deprecated in its own docstring. It mainly checks whether answerable SQL runs safely and whether unanswerable cases are handled. It does not perform the stronger gold-value comparison used by `eval_accurate.py`.

Use `eval_accurate.py` for the toy-data evaluation instead.

### 7.17 `app/eval_accurate.py` — toy-data answer evaluation

This script reads `eval/questions.csv`.

For every row:
1. Reads the question, question type, and expected answer.
2. Calls `get_sql()` using the selected prompt version.
3. Checks that unanswerable questions return `UNANSWERABLE`.
4. Runs generated SQL through the same safe database execution function.
5. Converts returned values into text and normalises case, commas, and trailing decimal notation.
6. Checks whether one of the expected answer tokens appears in the output.
7. Counts passes and reports results by question type.
8. Prints failures for inspection.

By default, the script selects v2. Flags `--v1`, `--v3`, and `--v4` select those prompt versions.

**How to interpret its score:** this is a small project evaluation based on whether expected answer tokens appear in the returned data. It is useful as a regression check, but it is not a comprehensive proof of semantic correctness. A substring match can pass even if a result contains extra or incorrectly grouped rows. The score applies to the particular test set, dataset, and execution environment.

### 7.18 `app/eval_real.py` — evaluation on district-level data

This is similar to `eval_accurate.py`, but it reads `eval/real_questions.csv` and uses:
- v5 by default.
- v6 when called with `--v6`.

It sends generated SQL to `chain.run_sql()`, checks for expected answer tokens, counts unanswerable cases, and prints failures.

This test is especially useful for testing the distinction between one district's value and a state total across multiple districts.

### 7.19 `app/redteam.py` — safety and adversarial tests

“Red teaming” means intentionally trying harmful or unexpected inputs to see whether an application handles them safely.

This script has two groups of tests.

**Question-level tests** include requests to delete or drop data, stacked instructions, prompt injection, personal information, off-topic requests, and crops outside the toy dataset. It calls the normal `answer()` workflow and checks whether the result is unanswerable or otherwise blocked.

**Direct-SQL tests** send dangerous SQL strings directly to `validate_sql()`. Each should raise `ValueError`.

At the end it reports how many question-level and direct-SQL tests passed. These are targeted test cases, not an exhaustive security audit.

### 7.20 `app/test_retry.py` — tests self-correction after query errors

This script deliberately replaces the SQL generator with a temporary test function.

- On the first call, it returns SQL that references a nonexistent column.
- On the next call, it delegates to the real SQL generator.
- The normal `answer()` function receives the SQL error and retries with that error included in the prompt.
- The test asserts that the second attempt succeeds and returns the expected production value.
- It then replaces the generator with one that always returns invalid SQL and checks that the configured retry limit is respected.

This is called failure injection: the test deliberately creates a failure so the retry mechanism can be checked.

### 7.21 `data/docs/agri_notes.md` — source material for document questions

This Markdown file contains agriculture notes. `hybrid.py` reads Markdown files in the docs folder, splits them into passages, searches them by word overlap, and returns matching text with the filename.

## 8. How SQL generation works — a fully explained example

Question:

> Top 3 states by wheat production in 2022?

The LLM should generate something similar to:

```sql
SELECT s.state_name, SUM(p.production_tonnes) AS total
FROM production p
JOIN states s ON p.state_id = s.state_id
JOIN crops c ON p.crop_id = c.crop_id
WHERE c.crop_name = 'Wheat'
  AND p.year = 2022
GROUP BY s.state_name
ORDER BY total DESC
LIMIT 3
```

Explanation:

- `SELECT s.state_name`: return the state name.
- `SUM(p.production_tonnes)`: add all matching production values.
- `AS total`: name the calculated column `total`.
- `FROM production p`: begin with the production records and give the table the short alias `p`.
- `JOIN states s ...`: connect each production row to its state.
- `JOIN crops c ...`: connect each production row to its crop.
- `WHERE c.crop_name = 'Wheat'`: keep wheat records only.
- `AND p.year = 2022`: keep records from 2022.
- `GROUP BY s.state_name`: calculate one total per state.
- `ORDER BY total DESC`: put the largest total first.
- `LIMIT 3`: return the first three states.

This illustrates why the model needs the catalog and why the prompts contain explicit aggregation and JOIN rules.

## 9. Prompt engineering: why are there six prompt versions?

The project does not treat the first prompt as final. It keeps earlier versions and adds rules after observing failure cases.

For example:

- A model can invent a table alias that does not exist. Later prompts restrict which aliases may be used.
- It can return individual rows when the question asks for a total. Later prompts explain when to use `SUM()`.
- It can use a self-join for comparing years. Later prompts recommend filtering with `IN (...)` and sorting by year.
- It can confuse a state-level question with a district-level question. v6 explicitly requires summing district rows for a state total.
- It can misinterpret “above a threshold”. v4 adds a threshold rule and an example.

This is an example of iterative prompt engineering: identify a failure, add a targeted instruction and example, then rerun the same evaluation set.

## 13. Important limitations and engineering considerations

Understanding limitations is part of understanding the project.

1. **The rule fallback is limited.** It handles a finite set of known question patterns; it cannot replace a real LLM.
2. **The upload application uses Ollama directly.** Unlike the curated-data path, `anydata.py` does not use the OpenAI provider fallback.
3. **The document retriever uses word overlap.** It does not use embeddings, vector search, or a vector database.
4. **The SQL safety validator is simple string-based validation.** It should be strengthened before production exposure.
5. **A pre-existing LIMIT is not reduced by the current validator.** It only appends a LIMIT when one is absent.
6. **The chart selector is heuristic.** It chooses the first categorical and first numeric columns; that may not always be the most meaningful chart.
7. **The generated natural-language summary is basic.** It reports rows and first-row/total information rather than asking a second LLM to explain every result.
8. **The upload table name is derived from the filename.** Uploading another file with the same cleaned filename replaces that table.
9. **The real-data table has an older year range.** It contains records for 2010–2017, not current-year agricultural statistics.
10. **Evaluation coverage is small.** Passing the included test suite does not prove correctness for all possible SQL questions, security attacks, or large-scale traffic.

These are useful improvement opportunities: a SQL parser and allow-list, enforced LIMIT cap, richer evaluation metrics, semantic document retrieval, better chart selection, and broader tests.

### 1-minute workflow explanation

“When a user asks a question, the request reaches the chain module. The chain calls the LLM module, which selects OpenAI, Ollama, or a limited rule-based fallback. ## 15. Recommended learning order for someone starting from zero

Do not try to memorise all files at once. Follow this order:

1. **Understand CSV, tables, rows, and columns.** Open the sample CSV files and inspect their contents.
2. **Learn basic SQL.** Practise SELECT, WHERE, JOIN, GROUP BY, SUM, AVG, ORDER BY, and LIMIT.
3. **Understand SQLite.** Learn how a `.db` file stores tables and how Python connects to it.
4. **Read `load_db.py`.** This is the easiest way to see how Python creates tables and inserts data.
5. **Read `catalog.json` and prompt v1.** Understand how the model learns the schema.
6. **Read `safety.py`.** Follow what happens to SQL before execution.
7. **Read `llm.py`.** Learn the provider selection and structured response handling.
8. **Read `chain.py`.** Connect all the pieces into the full question-answering pipeline.
9. **Run `test_retry.py` and `redteam.py`.** See how failures and unsafe inputs are tested.
10. **Read `eval_accurate.py` and prompt v1–v4.** Understand how the prompt evolved.
11. **Read `load_real.py` and prompt v5–v6.** Learn how the larger dataset changes the SQL rules.
12. **Read `hybrid.py`.** Learn the simple document retrieval route.
13. **Read `anydata.py` and `upload_app.py`.** Learn the separate upload workflow.
14. **Read the Streamlit UI files.** Understand how the backend is connected to the browser.

A good first hands-on exercise: run the demo database loader, ask one question, copy the generated SQL, and execute the SQL yourself in a SQLite viewer. Then change the question and observe how the SQL changes.

## 16. Final summary

The core idea of this project is:

**Natural-language question → prompt + schema → SQL generation → SQL safety checks → read-only database execution → result explanation and visualisation.**

The most important files to understand deeply are:

- `chain.py`: orchestrates the curated-data workflow.
- `llm.py`: generates SQL using the configured model provider.
- `safety.py`: validates the generated SQL.
- `catalog.json`: describes the database to the model.
- `anydata.py`: implements the upload-CSV query engine.
- `hybrid.py`: retrieves related local documentation and routes questions.
- `eval_accurate.py`, `eval_real.py`, and `redteam.py`: test answer handling and safety.

You do not need to understand every Python keyword on the first day. First understand the data and the end-to-end flow. Then study one function at a time, run it, change a small input, and observe its output.
